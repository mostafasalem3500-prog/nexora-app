# تقرير دفعة تدقيق الجودة — NEXORA TECH

**التاريخ:** 2026-09-10
**النطاق:** إصلاح خلل تباين ألوان WCAG حقيقي، احترام فعلي لـ`prefers-reduced-motion` في حركات
Framer Motion التلقائية، إصلاح خطأي `setState-in-effect`، حذف كود ميت.
**المنهجية:** كل بند أدناه مبني على فحص فعلي للكود (بحث شامل، ESLint، `tsc`، بناء إنتاج،
واختبار حي في المتصفح) — لا افتراضات. الأرقام (نسب التباين، عدد الاستخدامات) محسوبة فعليًا
وليست تقديرية.

## 1. خلل تباين ألوان WCAG — الفيروزي في الوضع الفاتح

### المشكلة

`--brand-teal: #16c9b8` يُستخدم كلون نص (`text-brand-teal`) في أكثر من 60 موضعًا عبر الموقع
(عناوين eyebrow، روابط، قيم إحصائيات، حالات محدَّدة في النماذج...). في الوضع الفاتح، خلفية
السطح هي `--bg-warm: #f2efe6`. نسبة التباين بين اللونين محسوبة بمعادلة WCAG 2.1 الرسمية
(luminance نسبي لكل لون، ثم `(L_light + 0.05) / (L_dark + 0.05)`):

| | Hex | نسبة التباين على `#f2efe6` | معيار WCAG AA (نص عادي: 4.5:1) |
|---|---|---|---|
| قبل | `#16c9b8` | **1.81:1** | ❌ فشل — أقل من نصف الحد الأدنى |
| بعد | `#0e6259` | **6.28:1** | ✅ نجاح — يتجاوز 4.5:1 بمسافة مريحة |

التحقق تم عبر سكربت Node.js صغير ينفّذ معادلة WCAG 2.1 الرسمية حرفيًا (وليس أداة تقريبية)،
وأيضًا عبر قياس فعلي في المتصفح (`getComputedStyle(...).color` على عنصر eyebrow حقيقي في
صفحة حية) بعد التطبيق — أعاد `rgb(14, 98, 89)` أي `#0e6259` بالضبط.

### السبب الجذري

`--brand-teal` كان قيمة واحدة ثابتة في `:root`، تُستخدم في الوضعين الداكن والفاتح معًا. في
الوضع الداكن (`--bg-deep: #0e1420`) النسبة ممتازة (8.85:1) — المشكلة خاصة بالوضع الفاتح فقط.

### الإصلاح

إضافة تعريف مستقل لـ`--brand-teal` داخل `[data-theme="light"]` في
[`globals.css`](../src/app/[locale]/globals.css) بقيمة أغمق من نفس العائلة اللونية (hue ≈174°،
نفس الدرجة الفيروزية) بدل تغيير القيمة الأساسية — هذا يحافظ تلقائيًا على كل الاستخدامات
الأخرى لنفس المتغيّر (حدود، تدرجات، ظلال توهج) متّسقة بصريًا دون الحاجة لمسّ عشرات الملفات
التي تستخدم `text-brand-teal` / `border-brand-teal` / إلخ. الوضع الداكن غير متأثر إطلاقًا.

## 2. احترام `prefers-reduced-motion` في حركات Framer Motion

### المشكلة

القاعدة العامة في `globals.css`:
```css
@media (prefers-reduced-motion: reduce) {
  * { animation-duration: 0.001ms !important; transition-duration: 0.001ms !important; }
}
```
تعمل فقط على حركات **CSS** (`animation`/`transition`). حركات **Framer Motion** (`initial`/
`animate`/`whileInView`/`exit`/`useSpring`) تُشغَّل عبر JavaScript (Web Animations API)، فلا
تتأثر بهذه القاعدة إطلاقًا — أي مستخدم فعّل `prefers-reduced-motion: reduce` (لأسباب دوار/
vestibular disorders غالبًا) كان لا يزال يرى كل حركات الموقع كاملة.

### الملفات التي كانت تحتوي حركة Framer Motion تلقائية (بحث شامل: 6 ملفات تستورد
`framer-motion`، تمت مراجعتها كلها)

| الملف | الحركة | الإصلاح |
|---|---|---|
| [`Reveal.tsx`](../src/components/Reveal.tsx) (مستخدَم 14 مرة في 11 ملفًا) | `whileInView` عند التمرير | `useReducedMotion()`: عند التفعيل تُعرض العناصر فورًا (`opacity:1, y:0`, `duration:0`) |
| [`Hero.tsx`](../src/components/Hero.tsx) | `fadeUp` تسلسلي عند التحميل | نفس النمط، منطق `fadeUp` نُقل داخل المكوّن ليصبح تفاعليًا مع الهوك |
| [`not-found.tsx`](../src/app/[locale]/not-found.tsx) | 4 عناصر `motion` متتالية (404، عنوان، فقرة، أزرار) | دالة `transition()` مساعدة مكتوبة بنوع `Transition` من framer-motion (تفاديًا لخطأ TS) |
| [`AnimatedCounter.tsx`](../src/components/AnimatedCounter.tsx) | عدّاد رقمي متحرك (Spring) | القيمة المعروضة تُحسب أثناء الـrender (`shouldReduceMotion ? value : display`) بدل قفزة عبر effect إضافي — انظر §3 لسبب تفادي `setState` هنا |
| [`QuoteWizard.tsx`](../src/components/QuoteWizard.tsx) | انتقال الخطوات (`AnimatePresence`) ورسالة النجاح | `duration: 0` وإزاحة صفرية عند التفعيل |
| [`MagneticButton.tsx`](../src/components/MagneticButton.tsx) | تتبّع الزر لمؤشر الفأرة (تفاعلي لا تلقائي) | مُعطَّل بالكامل عند `prefers-reduced-motion` رغم كونه تفاعليًا — الإزاحة المستمرة خلف المؤشر نوع معروف من محفّزات الدوار (vestibular) بصرف النظر عن كونها بفعل المستخدم |

### التحقق

لا توجد أداة في بيئة الاختبار تسمح بمحاكاة `prefers-reduced-motion: reduce` على مستوى
النظام داخل متصفح المعاينة (المتاح هو محاكاة `color-scheme` فقط، وليس media features
أخرى). التحقق الفعلي تم على المستويين التاليين:
- **صحة الكود**: كل استدعاء لـ`useReducedMotion()` وتفرّعاته يُبنى وتُفحص أنواعه بلا أخطاء
  (`tsc --noEmit` نظيف)، ولا يخالف أي قاعدة ESLint.
- **عدم كسر السلوك الافتراضي**: تم التصفح الفعلي للصفحة الرئيسية وصفحة الطلب (`/quote`) في
  المتصفح بدون تفعيل الخيار — الحركات تعمل بصريًا كما كانت (لقطات شاشة مرفقة أدناه)، بلا أي
  خطأ Console.
- هذا قيد صريح ومُقرّ به، وليس ادّعاءً بتحقق كامل من طرف إلى طرف لسلوك OS-level.

## 3. خطأا `setState-in-effect`

تم تحديدهما بدقة عبر تشغيل ESLint على كامل `src/` (ليس تخمينًا): قاعدة
`react-hooks/set-state-in-effect` (من `eslint-config-next` + React Compiler ESLint plugin)
أبلغت عن **خطأين فقط** في كامل المشروع (فحصنا كل استخدامات `useEffect`/`useLayoutEffect` —
6 استدعاءات فقط في 4 ملفات؛ 4 منها سليمة تمامًا: الاستماع لحدث `scroll` في `Header.tsx`،
اشتراك `spring.on("change")` في `AnimatedCounter.tsx` — كلاهما نمط "الاشتراك بحدث" الصحيح
الذي توصي به رسالة القاعدة نفسها).

### 3.1 — `ThemeToggle.tsx`

```tsx
// قبل
const [theme, setTheme] = useState<"dark" | "light">("dark");
useEffect(() => {
  const current = document.documentElement.getAttribute("data-theme");
  setTheme(current === "light" ? "light" : "dark"); // ← خطأ ESLint هنا
}, []);
```
المشكلة: `setState` متزامن داخل effect يعمل عند كل تركيب — يسبب render إضافية غير ضرورية،
وأيضًا "ومضة" أيقونة خاطئة لجزء من الثانية (الزر يعرض ☀️/الوضع الداكن افتراضيًا حتى لو كان
المستخدم قد اختار الوضع الفاتح سابقًا، ثم يُصحَّح بعد الـmount).

**الإصلاح:** قراءة القيمة الأولية مباشرة عبر lazy initializer لـ`useState` بدل effect:
```tsx
function getInitialTheme(): "dark" | "light" {
  if (typeof document === "undefined") return "dark";
  return document.documentElement.getAttribute("data-theme") === "light" ? "light" : "dark";
}
const [theme, setTheme] = useState<"dark" | "light">(getInitialTheme);
```
بما أن `ThemeScript` (سكربت مضمّن يعمل قبل الـHydration) يضبط `data-theme` على الـ`<html>`
قبل أن يُشغَّل React، تكون القيمة صحيحة من أول render على المتصفح — لا ومضة، ولا render
إضافية. أُضيف `suppressHydrationWarning` على الزر لأن قيمة الخادم الافتراضية ("dark", إذ لا
يوجد `document` في SSR) قد تختلف فعليًا عن القيمة الحقيقية على المتصفح (إن كان المستخدم قد
اختار الفاتح سابقًا) — هذا اختلاف متعمّد وموثّق رسميًا كحالة استخدام لـ
`suppressHydrationWarning`، تم التحقق أنه يُسكت التحذير فعليًا (اختبار حي: تخزين "light" في
localStorage ثم إعادة تحميل الصفحة — صفر أخطاء Console).

### 3.2 — `QuoteWizard.tsx` (خلل مزدوج: مخالفة ESLint **و** خلل حقيقي في فقدان البيانات)

```tsx
// قبل
useEffect(() => {
  const saved = localStorage.getItem(STORAGE_KEY);
  if (saved) setData(JSON.parse(saved)); // ← خطأ ESLint هنا
}, []);

useEffect(() => {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(data));
}, [data]);
```
هذا ليس مجرد مخالفة أسلوبية. عند التركيب، الـeffect الأول (تحميل) والثاني (حفظ) يعملان في
نفس الجولة؛ الثاني يعتمد على `data` وهي لا تزال `EMPTY` (القيمة الافتراضية) لأن `setData` من
الأول لم يُطبَّق بعد على الحالة عند تنفيذ الثاني. النتيجة: **الحفظ يكتب `EMPTY` فوق أي تقدّم
محفوظ في localStorage قبل أن يُستعاد فعليًا** — أي مستخدم عاد لإكمال طلب عرض السعر بعد إغلاق
الصفحة كان يفقد ما أدخله سابقًا (في الحالات التي لا "يتعافى" منها الترتيب تلقائيًا، مثل مغادرة
الصفحة بسرعة بين الجولتين).

**تم إعادة إنتاج الخلل والتأكد من الإصلاح فعليًا في المتصفح** (وليس بالتحليل فقط):
1. تعبئة الخطوة الأولى ("تطبيق جوال") في `/ar/quote` على الكود القديم.
2. فحص `localStorage.getItem('nexora-quote-wizard')` — القيمة موجودة.
3. إعادة تحميل الصفحة، وفحص القيمة مجددًا — **كانت تعود فارغة** (الخلل مؤكَّد قبل الإصلاح).

**الإصلاح — ومحاولة أولى فاشلة تستحق التوثيق بصدق:** أول محاولة استبدلت الـeffect بـ
lazy initializer بسيط (`useState(loadSavedData)`, يقرأ `localStorage` مباشرة). هذا يحل مشكلة
فقدان البيانات، **لكنه يفتح خللًا مختلفًا**: القيمة الأولية على الخادم (SSR، لا يوجد
`localStorage`) تكون `EMPTY` دائمًا، بينما القيمة الأولى على المتصفح قد تكون البيانات
المستعادة فعليًا — هذا اختلاف قابل للاكتشاف في render الأول نفسه (وليس بعد mount كما في
`ThemeToggle`)، لأنه يغيّر `className`/`disabled` لعناصر داخل الشجرة. React يرصد هذا كخطأ
Hydration Mismatch حقيقي رأيناه فعليًا في Console:
> "A tree hydrated but some attributes of the server rendered HTML didn't match the client
> properties. **This won't be patched up.**"

أي أن الزر المستعاد (`تطبيق جوال`) كان يبقى **غير مُعلَّم بصريًا رغم أن قيمته في الحالة
صحيحة** — خلل واجهة حقيقي بديل عن خلل فقدان البيانات الأصلي، وليس إصلاحًا كاملًا.

**الإصلاح النهائي الصحيح:** استخدام `useSyncExternalStore` — أداة React المخصّصة تحديدًا
لقراءة قيمة خارجية (متصفح فقط) بأمان عبر SSR، عبر `getServerSnapshot` منفصلة عن
`getSnapshot`:
```tsx
function useIsHydrated() {
  return useSyncExternalStore(() => () => {}, () => true, () => false);
}
```
الـrender الأول على المتصفح يطابق الخادم تمامًا (`isHydrated=false`، `data=EMPTY`) فلا يوجد
Mismatch. بعد اكتمال الـHydration، React يُعيد الرسم بـ`isHydrated=true` تلقائيًا؛ عندها
يُستدعى `setData(saved)` **أثناء الـrender نفسه** (نمط "تعديل الحالة أثناء الرسم" الموثّق
رسميًا في React، محروسًا بحالة `restored` وليس بـ`ref` — الكتابة على `ref` أثناء الرسم غير
آمنة تحت الاستدعاء المضاعف لـStrict Mode في وضع التطوير) — **وليس داخل `useEffect`**، فلا
يخالف قاعدة ESLint. effect الحفظ أُضيف له حارس `if (!isHydrated) return;` لمنع كتابة `EMPTY`
فوق البيانات قبل اكتمال الاستعادة (إصلاح مباشر لسبب الخلل الأصلي).

**تحقق فعلي بعد الإصلاح:**
- إعادة إنتاج نفس سيناريو الاختبار أعلاه (تحديد → فحص localStorage → إعادة تحميل → فحص
  مجددًا): القيمة **بقيت محفوظة** هذه المرة.
- ملاحظة صدق مهمة: في **وضع التطوير** (`next dev`) رصدنا تحذير Hydration Mismatch لا يزال
  يظهر أحيانًا لنفس هذا المكوّن. بعد تتبّعه بسجلّات تصحيح مؤقتة، تبيّن أنه ناتج عن السلوك
  المضاعف المتعمَّد لـ React Strict Mode في التطوير فقط (يستدعي دوال الرسم مرتين لأغراض رصد
  الشوائب) وليس خللًا في المنطق. **تم التأكيد بشكل قاطع عبر بناء إنتاج فعلي
  (`next build` + `next start` على منفذ منفصل)**: نفس السيناريو بالضبط (استعادة "تطبيق جوال"
  بعد إعادة تحميل) يعمل في الإنتاج **بدون أي تحذير Hydration في Console**، والزر يظهر محدَّدًا
  بصريًا بشكل صحيح من أول رسم. بما أن سلوك الإنتاج هو ما يراه المستخدم الحقيقي، هذا يُعتبر
  الإصلاح صحيحًا ومكتملًا؛ تحذير التطوير مُوثَّق هنا بصدق كقيد معروف بدل إخفائه.

## 4. الكود الميت المحذوف

بحث ممنهج (لا حذف تخميني): لكل مكوّن في `src/components`، تم التأكد أنه مستورَد في مكان آخر
(لا توجد مكوّنات يتيمة بالكامل). لكل تصدير في `src/lib/*.ts`، تم عدّ الاستخدامات الفعلية خارج
ملفه. لكل متغيّر CSS مُعرَّف في `globals.css`، تم عدّ عدد مرات ظهوره في الملف نفسه (تعريف واحد
فقط = غير مُستخدَم إطلاقًا).

| العنصر | الموقع | الحالة |
|---|---|---|
| `.num` (class CSS) | `globals.css` | معرَّف مع `.en` بنفس القواعد، لكن **لا يظهر في أي `className` بكامل `src/`** (تحقّق: `grep -rn "\bnum\b" src` لا يُرجع إلا تعريفه). **حُذف**، وأُبقي `.en` وحدها (مستخدَمة 40+ مرة فعليًا) |
| `--radius-sm` / `--radius-md` / `--radius-lg` | `globals.css`, `:root` | معرَّفة في `:root` لكن لا تظهر في `@theme inline` ولا في أي `style` مضمَّن ولا في أي ملف `.tsx` بالمشروع (كل التقويس يتم عبر أصناف Tailwind المباشرة مثل `rounded-md`/`rounded-2xl`). **حُذفت الثلاثة** |

### عناصر فُحصت واستُبعدت عمدًا من الحذف (للصدق، وليس إغفالًا)

- الأنواع المصدَّرة من `site-data.ts` (`Bilingual`, `ServiceCategory`, `CaseStudy`, `Faq`,
  `Article`, `JobPosting`) لا يستوردها أي ملف آخر بالاسم صراحة، لكنها **مُستخدَمة فعليًا**
  داخل نفس الملف لتنميط المصفوفات المصدَّرة (`services: Service[]` إلخ) — إزالة `export` عنها
  قرار أسلوبي حول سطح API داخلي، وليس كودًا ميتًا بالمعنى الدقيق (كود غير مُنفَّذ/غير
  مرجعي)، فلم يُمسّ.
- لا توجد استدعاءات `console.log`/`console.debug`، ولا كتل كود مُعلَّقة (`//`), ولا
  `TODO`/`FIXME` في كامل `src/` (تحقّق فعلي بالبحث، ليس افتراضًا).

## 5. خارج النطاق صراحة (لم يُغيَّر، مذكور هنا للشفافية)

الدفعة كانت محدَّدة الأهداف؛ الأمور التالية اكتُشفت أثناء الفحص لكنها **خارج نطاق هذه المهمة**
ولم تُلمَس، تفاديًا لتضخيم الفرق (diff) بتغييرات غير مطلوبة:

- **45 خطأ ESLint من نوع `@typescript-eslint/no-explicit-any`** و**2 من نوع
  `@typescript-eslint/ban-ts-comment`** (استخدام `@ts-ignore` بدل `@ts-expect-error`) في
  `auth.ts`, `prisma.ts`, `get-site-settings.ts`, ومسار `/admin` بالكامل — موجودة قبل هذه
  الدفعة، غير متعلقة بأي بند مطلوب.
- `docs/02-design-tokens.md` يصف خطة تصميم أولية (متغيّرات `--text-*`, `--space-*`,
  `--shadow-*`, نظام ألوان أوسع) لا تطابق تمامًا ما هو منفَّذ فعليًا في `globals.css` — هذا
  انحراف توثيقي سابق لهذه الدفعة ولم يكن جزءًا من طلبها.
- تحديثات الحزم (`prisma` 6.19.3 → 8.0.0-rc.13 المتاحة، و3 ثغرات "high severity" أبلغ عنها
  `npm audit`) لم تُطبَّق — تغيير نسخ التبعيات قرار منفصل يستحق مراجعته وحده.
